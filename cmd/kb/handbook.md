#### 典型并发/并行访问引起问题的场景

1. 写前读（read before write）
   1. 同时操作单条记录：只需要该记录的结果
      1. 乐观锁
   2. 同时关联整个表：即先需要全表查询的结果，后决定是否执行
      1. 分布式锁
      2. 数据库层面：间隙锁+记录锁
2. 双写问题：last write win
   1. 同时追加一个数组（队列）
      1. 处理方式：加锁，互斥访问
   2. 保证顺序写入
      1. 消息队列映射同一个partition，并被一个消费者消费
3. 写不同的存储介质
   1. 场景：写缓存和数据库
      1. 旁路写
         1. 如果同一个key经常命中导致频繁更新：可以保存在其他地方，延迟写，或者不删缓存
         2. 如果删除缓存失败
            1. 增加重试机制
            2. 发失败的消息到dead queue，隔一段时间更新一次
      2. 透传缓存：由缓存先更新自己，再由他更新数据库
      3. 写回法
         1. 读场景
            1. 读缓存，如缓存没有，读数据库
         2. 写
            1. 写缓存，预留写数据库的标志
            2. 异步写数据库，成功则删除标志，失败则超时，删除缓存
   2. 场景：写数据库和其他存储介质
      1. 数据一致性问题：原子性
      2. saga模式+中心化协调器

#### topK, 大文件求共同数据

1. 两个1G的url大文件，1M小内存环境，如何获得共同的url（1）
   1. 先将两个大文件拆成2000个小文件
   2. 使用hash表，对加载到内存的A， B小文件的每个url计算hash值取模2000，存入对应的A_i, B_i中
   3. 再将A_i，B_i加载到内存，对A中的url进行遍历和加入集合中，如果B中有的话就是公共url
   4. 如果哈希发生倾斜，文件爆了怎么办？
      1. 内部递归再哈希，拆成更小的文件，每次只加载小文件，进行set的比较

2. 一个1G的url大文件，1M小内存环境，如何获得文件的topK
   1. 先将大文件拆成2000个小文件
   2. 依次将整个 file_i 读入内存，用一个 HashMap<String, Integer> 统计其中所有文本出现的频次。
   3. 用容量为k的小根堆堆顶元素和当前比较，如果大则堆顶弹出，对元素进行频次的记录和调整
   4. 返回堆中最后剩下的k个元素

3. 怎么对大文件进行外部排序？
   1. 对大文件进行切分，切成n个小文件，对这n个小文件直接内存排序
   2. 对内存进行精确分配，对每个小文件读取一条数据，最终全局维护一个最小堆。
   3. 对这个最小堆弹出一个栈顶，并补足对应文件里的下一条数据，继续进行比较
   4. 如果输出缓冲区满了，则输出到磁盘。

### 缓存

1. 缓存击穿，穿透，雪崩（2）
   1. 击穿：缓存中的**某个热点数据过期**了，此时大量的请求访问了该热点数据，就无法从缓存中读取，直接访问数据库
      1. 解决方式：
         1. 分布式锁：用锁拦截多余的流量访问
         2. 逻辑过期时间：在缓存里一直有效，只是字段里包含过期时间
   2. 穿透：用户访问的数据，**既不在缓存中，也不在数据库中**，导致请求在访问缓存时，发现缓存缺失，再去访问数据库时，发现数据库中也没有要访问的数据，于是只能写数据库，再更新缓存。
      1. 解决办法
         1. 第一种方案，非法请求的限制；
         2. 第二种方案，缓存空值或者默认值；
         3. 第三种方案，使用布隆过滤器快速判断数据是否存在，避免通过查询数据库来判断数据是否存在，布隆过滤器可以迅速判断key是否不在缓存中
   3. 雪崩：**大量缓存数据在同一时间过期（失效）或者 Redis 故障宕机**时，如果此时有大量的用户请求，都无法在 Redis 中处理，于是全部请求都直接访问数据库
      1. 解决办法
         1. 均匀设置过期时间
2. 缓存和数据库的更新方法
   1. 旁路更新
      1. 读：从缓存读，若不命中，从数据库读，回写缓存
      2. 写：先写数据库，后删缓存
      3. 缺点：
         1. 因为更新失败删除缓存，导致频繁访问数据库，更新缓存
         2. 如果删除失败，仍然会读缓存的老数据
            1. 延迟双删：延迟一段时间再删除
            2. 使用Canal监听binlog，自动更新缓存
   2. 代理更新：需要使用专业的缓存组件
   3. write through
      1. 業務發起寫入： 應用程序調用緩存的寫入接口。
      2. 緩存同步寫入底層： 緩存接收到數據後，立刻同步將數據寫入數據庫。
      3. 返回成功： 數據庫寫入成功後，緩存才向應用程序返回「寫入成功」。
   4. 写回模式（write-back）：
      1. 業務發起寫入： 應用程序調用緩存的寫入接口。
      2. 同时cache写入数据库成功后回调的key，写入成功后即可返回。
      3. 异步，也可批量寫入底層： 緩存接收到數據後，立刻同步將數據寫入數據庫。
      4. 同时写入数据库成功后回调的key，写入成功后即可返回。和上一步在一个事务中完成
      5. 如果cache挂了
         1. WAL机制：先在磁盘文件末尾追加写入的sql
         2. redis的AOF落盘
         3. 升级redis集群为高可用

### 数据库

1. 事务隔离级别（2）

   1. 未提交读：脏读问题，初始什么都不限制的状态
   2. 已提交读：解决脏读，但是不可重复读
      1. 只能读取已经提交过的最新记录（**只有起点状态相比于未提交读有所限制**），不屏蔽别的事务的**增删改操作**
   3. 可重复读：解决不可重复读，但是you幻读
      1. 记录的读取操作对其他事务的修改操作屏蔽，不屏蔽别的事务对数据表的**增删操作**
   4. 串行化
   5. 隔离级别的实现方式
      1. min_trx_id：在生成 ReadView 时，所有活跃（未提交）事务中，事务ID的最小值
      2. max_trx_id：在生成 ReadView 时，系统下一个将要分配的事务ID，也就是当前最大事务ID
      3. m_ids: 生成 ReadView 时，所有活跃（未提交）事务的ID列表
      4. 已提交读、可重复读：采用undo log对应的版本链，找到能够读取的最新版本
         1. - 如果 trx_id == creator_trx_id：说明这个记录版本是当前事务自己修改的，对活跃事务可见。
            - 如果 trx_id < min_trx_id：说明该版本记录在事务开启前已提交，对活跃事务可见。
            - 如果 trx_id >= max_trx_id：说明该版本记录是在 Read View 生成后才开启的事务生成的，对活跃事务不可见。
            - 如果 min_trx_id <= trx_id < max_trx_id：
              - 若 trx_id 在 m_ids 列表中，说明该事务还未提交，对活跃事务不可见。
              - 若不在列表中，说明事务已提交，对活跃事务可见。
      5. 幻读：采用间隙锁锁指定区间的方式解决，其他事务的插入删除会被阻塞

2. 事务ACID特性（3）：

   1. 原子性：指整个数据库事务是不可分割的工作单位。只有使据库中所有的操作执行成功，才算整个事务成功；事务中任何一个SQL语句执行失败，那么已经执行成功的SQL语句也必须撤销，数据库状态应该退回到执行事务前的状态。
   2. 一致性：**指数据库事务不能破坏关系数据的完整性以及业务逻辑上的一致性**。例如对银行转帐事务，不管事务成功还是失败，应该保证事务结束后ACCOUNTS表中Tom和Jack的存款总额为2000元。
   3. 隔离性：指的是在并发环境中，当不同的事务同时操纵相同的数据时，每个事务都有各自的完整数据空间。由并发事务所做的修改必须与任何其他并发事务所做的修改隔离。事务查看数据更新时，数据所处的状态要么是另一事务修改它之前的状态，要么是另一事务修改它之后的状态，事务不会查看到中间状态的数据。
   4. 持久性：指的是只要事务成功结束，它对数据库所做的更新就必须永久保存下来。即使发生系统崩溃，重新启动数据库系统后，数据库还能恢复到事务成功结束时的状态。

13.  mysql三种log的区别

- binlog：MySQL Server 层面上记录的所有逻辑操作。
  - 主从复制： Master 把 binlog 发给 Slave，Slave 执行一遍，实现数据同步。
  - 数据恢复： 如果你不小心删库了，可以拿全量备份加上 binlog 里的操作指令，把数据“跑”回来。
- redo log：redo log 是为了保证事务的持久性（Durability）。
  - 当数据库宕机时，内存中尚未同步到磁盘的数据会丢失。重启后，InnoDB 会读取 redo log，把还没来得及写入磁盘的物理修改“重做”一遍。
  - 它是循环写的（空间固定，写满会覆盖旧日志）。它记录的是“在某个数据页的某个偏移量上做了什么修改”，属于物理日志。
  - WAL (Write-Ahead Logging)。先写日志到磁盘，等系统空闲时再异步把内存数据刷到磁盘。
- undo log：为了保证事务的原子性（Atomicity）和隔离性（Isolation）。
  - 回滚： 如果事务执行一半失败了，或者你执行了 ROLLBACK，undo log 会把数据逻辑地恢复到修改前的样子。
  - MVCC (多版本并发控制)： 当一个事务在读数据，而另一个事务在改数据时，读事务会通过 undo log 读到历史版本的快照，实现非阻塞读。
  - 它是逻辑日志。比如你 INSERT 了一条记录，undo log 就记录一条对应的 DELETE；你 UPDATE 了一行，它就记录原值

   2. 根据对象大小采用三种分配策略，首先是P (Processor) 的 mcache (本地缓存)。其中 size classes 是关键——它将内存划分为约 70 种固定大小的块（如 8B, 16B, 32B... 32KB），避免外碎片。
      1. 微对象 (Micro, < 16B)：不单独分配，直接存于 mcache 中的 tiny allocator，用于合并极小字符串、小对象，极大减少内存碎片和分配次数。
      2. 小对象 (Small, 16B ~ 32KB)：根据大小向上取整到对应的 size class，从 mcache 的对应空闲链表快速分配。
   3. M (Machine) 的 mcentral (中心缓存)：当 mcache 不够用时，会从对应大小的 mcentral 中批量获取。访问 mcentral 需要加锁，但频率已大大降低。
   4. OS 的 mheap (堆)：当 mcentral 也不足时，向操作系统申请大块内存（通常为 64KB 的 span）。mheap 负责管理大块内存和垃圾回收后的内存回收。加锁访问
   5. 大对象 (Large, > 32KB)：直接从 mheap 分配，以整页为单位（页大小通常为 8KB），这种方式会直接走中心化路径，但大对象数量少，开销可控。
10. golang锁竞争两种模式（1）
   1. 通常模式
      1. 锁被释放后，唤醒的等待者需与新来的 goroutine 共同竞争锁的所有权
      2. 新来的goroutine来说，拥有“先天优势”。它们正在CPU上运行，且可以多个同时自旋，因此更容易抢到锁
      3. 性能极佳，减少了 goroutine 的频繁挂起和唤醒开销
      4. 高并发、竞争激烈的场景，可以最大化系统吞吐量。
   2. 饥饿模式
      1. 锁的所有权从解锁的 goroutine 直接移交给等待队列头部的 goroutine
      2. 不自旋，不参与抢锁。它们会直接自觉地去等待队列尾部排队
      3. 性能相对较低，但提供了严格的 FIFO 顺序，保证了公平性
      4. 防止尾部延迟（长尾效应） ，确保所有 goroutine 最终都能获得锁。
   3. 两种模式的切换时机
      1. 进入饥饿模式
         1. 当 goroutine 等待超过 1 毫秒，且当前不是饥饿模式时
      2. 退出饥饿模式：
         1. 获得锁时等待时间 < 1 毫秒
         2. 或是等待队列中最后一个 goroutine
   4. 锁的实现原理
      1. state：数位，存储对应的信息
         1. 锁定位（Locked）：1 表示已被某个 goroutine 持有
         2. 有等待者位（Woken）：1 表示已有 goroutine 被唤醒，正在尝试获取锁
         3. 饥饿模式位（Starving）：1 表示当前处于饥饿模式
         4. 等待者计数（Waiter count）（29位）：正在等待锁的 goroutine 数量
      2. sema：信号量
      3. 加锁：
         1. 如果 state 为 0，直接通过 CAS 将 Locked 位设为 1，加锁成功。这是最快的情况。
         2. 如果快速路径失败，进入 lockSlow() 函数
            1. 检查当前锁的模式
            2. CAS更新state状态，否则排队等待信号量
      4. 解锁
         1. 直接原子操作清除 Locked 位，如果 new 变为 0，说明没有等待者，解锁完成
         2. 如果有等待者，则唤醒
      5. 自旋：自旋期间会尝试设置 Woken 位，表明已有 goroutine 在自旋而不是等待，避免不必要的被动唤醒。自旋需要满足如下条件：
         1. CPU 核心数 > 1
         2. 当前是正常模式
         3. 自旋次数 < 4 次
         4. 多核且有可运行的 P（处理器）

14. GMP模型（4）

​	G代表goroutine，P代表调度器，M代表内核线程数，不是内核数。指的是通过调度器，goroutine和内核线程的映射关系。调度器本身也可以有调度队列存放协程。

  - 通过保存和修改CPU寄存器的值来达到切换goroutine的目的。
  - 一般采用抢占式时间片的调度方式，从局部调度器或全局调度器队列中选取goroutine运行

调度算法（1）

- 查看全局队列是否有goroutine，有就消费

10. 垃圾回收机制（3）

基本上回收堆的内存。除非栈的内存逃逸。

- 基本内存分配规则
  1. 指针只能在堆上分配对应的存储空间
  1. 变量，函数内部局部变量在栈中分配

- 内存逃逸（3）

由于编程语言不知道变量所在内存的生命周期，发生从栈中到堆中的变量赋值，典型情况有：

- 函数返回指针，该返回值不能跟随局部调用栈中
- **发送参数值到 channel 中。** 在编译时，是没有办法知道哪个 goroutine 会在 channel 上接收数据。所以编译器没法知道变量什么时候才会被释放。
- **在一个切片上存储指针或带指针的值。** 一个典型的例子就是 []*string 。这会导致切片的内容逃逸。尽管其后面的数组可能是在栈上分配的，但其引用的值一定是在堆上。
- **slice 的背后数组被重新分配了，因为 append 时可能会超出其容量( cap )。** slice 初始化的地方在编译时是可以知道的，它最开始会在栈上分配。如果切片背后的存储要基于运行时的数据进行扩充，就会在堆上分配。
- **在 interface 类型上调用方法。** 在 interface 类型上调用方法都是动态调度的 —— 方法的真正实现只能在运行时知道。想像一个 io.Reader 类型的变量 r , 调用 r.Read(b) 会使得 r 的值和切片 b 的背后存储都逃逸掉，所以会在堆上分配。

- 黑白灰-三色标记法
  1. 刚开始白色节点
  2. 访问过程中为灰色节点
  3. 访问结束为黑色节点，此时删除白色节点的存储空间

- 写屏障是什么
  - 写屏障是一种在内存写入操作前后插入的额外处理逻辑，用于在并发标记阶段维护对象图的正确性。当程序修改指针时，写屏障会确保垃圾回收器能够正确跟踪所有可达对象。允许垃圾回收程序和用户程序并行执行，而不会导致错误回收。
  - 防止漏标记：当标记线程正在扫描对象图时，用户程序可能同时修改指针关系，写屏障确保这些修改不会导致存活对象被错误回收。具体来说在用户程序执行前：
    - 如果被覆盖的指针指向一个白色对象，将其标记为灰色
    - 如果新的指针指向一个白色对象，将其标记为灰色
  - 维护三色不变性：Go 使用三色标记法(黑、灰、白)，写屏障帮助维护以下不变性：
    - 强三色不变性：黑色对象不会指向白色对象
    - 弱三色不变性：黑色对象可以指向白色对象，但必须通过灰色对象可达

2. 内存分配机制
   1. 总的分为三种大小类型的分配
      1. Arena（竞技场）： 最大的单位，通常是 256 KB。它是直接向操作系统申请的连续内存块。
      2. Pool（内存池）： 一个 Arena 被切分成多个 Pool，每个 Pool 大小通常是 4 KB（正好对应操作系统的一个内存页）。一个 Pool 只能存放同一种大小的对象。
      3. Block（内存块）： Pool 内部被进一步切分成固定大小的 Block。Block 的大小以 8 字节对齐，从 8 字节到 512 字节不等（例如：8B, 16B, 24B ... 512B）。
   2. 大对象（ > 512 字节）： 直接绕过 PyMalloc，调用标准 C 库的 malloc() 向操作系统申请空间。
   3. 小对象（ <= 512 字节）：Python 根据对象大小，计算出它属于哪一个大小级别（Size Class）。
   4. 去对应的 Pool 中找一个空闲的 Block 分配给该对象。如果对应的 Pool 满了，就从当前 Arena 里开辟一个新的 Pool；如果 Arena 也满了，就新建一个 Arena。

   3. 如果想要判断对方是否正在输入，可以另起一组字典映射，当客户端检测到输入事件时发送消息给socket，socket再发送消息给接收方

#### TCP/IP

1. 三次握手（1）
   1. 理论上至少要三次握手才行
   2. 协商哪些数据
      1. 初始序列号
      2. 最大报文段长度
      3. 窗口缩放因子
      4. SACK 已选择确认
      5. 时间戳
2. ARP和RARP
   1. ARP：IP转MAC
      1. ARP攻击：局域网内传递虚假的ARP报文，使目标主机认为自己是网关，进而hack数据包
   2. RARP：MAC转IP
3. 四次挥手（1）
   1. 理论上可以三次完成
   2. 没有内容发送，此时发出FIN报文
   3. 对方接受，此时对方还可以发送数据过来
   4. 对方发完之后传送FIN报文
   5. 接收到之后发送ACK确认，2MSL后关闭连接
      1. 因为确认没有旧连接的包，且自己发出的报文已经被对方接收，所以可以关闭连接，否则等待对方再次发送的FIN报文
      2. 为什么要等2MSL（1）
         1. 确认是当前连接，因为在2MSL内，对方可能会重复发送FIN报文，导致无法关闭连接。
   6. time_wait状态的端口可以建立新连接吗（1）
      1. 可以，标识连接的本质是源ip端口，目的IP端口的四元组，只要四元组不同就是不同的新连接
4. 用途
   1. 可靠通信，适合点对点，安全通信
5. 拥塞控制
   1. 慢开始：指数方式开始增大包大小
   2. 快重传：设置快重传的值为拥塞时候的一半，继续慢开始

6. IPv4 和 IPv6区别
   1. IPv6 具有更大的地址空间。
   2. IPv6 使用更小的路由表。
   3. IPv6 增加了增强的组播（Multicast）支持以及对流的支持（Flow Control）。
   4. IPv6 加入了对自动配置（Auto Configuration）的支持。
   5. IPv6具有更高的安全性。

7. 对头阻塞（1）
   1. TCP 是按顺序传输的，如果前面一个数据包丢了，后面的数据即使收到了，也不能立即交给应用层。这就造成后面数据被前面的丢包“拖住”了 —— HOL 阻塞。
   2. 服务器按顺序处理包数据，如果卡在开始，则响应同样慢

8. 有两个网卡设置了相同的网段的不同IP，有什么问题
   1. 如果是弱主机模式，会导致TCP连接可能中断，ARP解析错误等问题

#### UDP

1. 和TCP的区别
   1. TCP校验更严格，传输更可靠
   2. UDP适合多播，没有连接建立过程，TCP适合点对点
2. 用途
   1. 不可靠通信，没有拥塞控制，确认机制，适合多播，广播

#### websocket

1. 先用HTTP建立连接
2. 随后client请求升级此连接为socket连接
   1. 协议升级是为了避免TCP的慢开始
3. 之后可以用socket的通信加密方式进行数据传输

#### 对称加密和非对称加密

对称加密

- 双方共用一个密钥进行加密和解密

非对称加密

- 加密通信：亮明自己的公钥，对方用这个公钥加密，自己用自己的私钥解密
- 数字签名：使用自己的私钥加密，对方用你的公钥解密

实例：SSL加密通信的建立过程

先采用非对称加密的方式，协商出之后对称加密的公钥。之后采用该公钥对称加密通信。

1. 客户端生成公钥，发送给服务端
2. 服务端返回确认后，客户端用私钥加密自己后续对称加密要用的密钥，发送给客户端
3. 客户端收到后返回确认，之后双方采用该私钥对称加密通信

#### HTTP

1. 1.0特点
   1. 无状态，无连接，每请求一个资源前必须先建立连接
2. 1.1特点
   1. 支持长连接，使用connection的header字段、
   2. 支持缓存，使用cache-control等相关字段
   3. 可以同时并发多个资源请求，但是也只能按顺序一个一个返回
3. 2.0特点
   1. 二进制结构传输，有别于1.x中的request header-content-response模式
   2. 同个域名只需要一个TCP连接
   3. 真正实现了并行传输
   4. 支持服务端推送
4. HTTPS特点
   1. 多了一步，客户端验证服务器证书
   1. 握手之后双方协商加密解密算法
   1. 之后报文采用密文传输
5. Cookie和Session的区别和联系
   1. 一个在客户端，一个在服务器端
   2. session的id会被存成response header的set-cookie字段返回，客户端之后用这个字段请求session信息，比如用户信息
6. 从输入网址到获得页面的过程
   - 浏览器查询 DNS，获取域名对应的 IP 地址：
     - 具体过程包括浏览器搜索自身的 DNS 缓存、搜索操作系统的 DNS 缓存、读取本地的 host 文件和向本地 DNS 服务器进行查询等。
     - 对于向本地 DNS 服务器进行查询，如果要查询的域名包含在本地配置区域资源中，则返回解析结果给客户机，完成域名解析（此解析具有权威性）。如果要查询的域名不由本地 DNS 服务器区域解析，但该服务器已缓存了此网址映射关系，则调用这个IP地址映射，完成域名解析（此解析不具有权威性）。
     - 如果本地域名服务器并未缓存该网址映射关系，那么将根据其设置发起递归查询或者迭代查询。
   - 浏览器获得域名对应的 IP 地址以后，浏览器向服务器请求建立连接，发起三次握手。
   - TCP/IP 连接建立起来后，浏览器向服务器发送 HTTP 请求。
   - 服务器接收到这个请求，并根据路径参数映射到特定的请求处理器进行处理，并将处理结果及相应的视图返回给浏览器。
   - 浏览器解析并渲染视图，若遇到对 js 文件、css 文件及图片等静态资源的引用，则重复上述步骤并向服务器请求这些资源。
   - 浏览器根据其请求到的资源、数据渲染页面，最终向用户呈现一个完整的页面。
